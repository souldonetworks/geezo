# Single-Binary Packaging (Bun compile) — Design

## Purpose

Package the existing GSD Run Dashboard (Node/Express backend + React/Vite frontend + Claude Code hook) as a single, self-contained native executable per target platform, so it can be shipped and run without Node.js installed on the target machine at all — including for the Claude Code hook integration.

## Background / why not Docker

Containerizing was the original ask, but the app's "convert to GSD project" feature launches a real Terminal/iTerm window on the host via `osascript` — this requires access to the host's GUI/window server, which no container (regardless of volume mounts) can provide. The user chose to keep running the app natively rather than work around that, and pivoted to wanting an easy-to-ship single-binary distribution instead of containerization.

## Non-goals

- Not a rewrite. The existing Node/Express/React code is reused as-is; only a thin unified CLI wrapper and an asset-embedding step are added.
- Does not change the existing `npm run dev` / `npm start` / `npm test` developer workflow — those keep working exactly as today, unaffected by this feature.
- Does not attempt to make the "convert to GSD project" feature work cross-platform or in any containerized/headless context — it remains macOS-only (`osascript`) regardless of packaging format, same as today.
- Does not set up CI/release automation for the multi-platform build — `npm run build:binary` is a manual, locally-run packaging step for now.

## Architecture

A new unified CLI entrypoint, `server/cli.js`, is compiled with `bun build --compile` into a standalone executable with three subcommands:

- **`serve`** (default when no subcommand given): starts the Express app — same route modules as `server/app.js` — but serves the frontend from an embedded asset manifest instead of `express.static(web/dist)`.
- **`hook`**: reads a Claude Code hook JSON payload from stdin and runs the same logic as `hooks/gsd-web-hook.js`'s `handle()`, then always exits 0.
- **`install-hook`**: merges hook entries into `~/.claude/settings.json`, pointing them at `<this binary's own path> hook` instead of `node hooks/gsd-web-hook.js` — so the whole tool, including live activity tracking, runs without Node.js installed anywhere.

The existing Node/npm-based code (`server/app.js`, `server/server.js`, `hooks/gsd-web-hook.js`, `scripts/install-hook.js`) is preserved and continues to work exactly as today for local development. `server/cli.js` is an additional entrypoint, not a replacement.

## Asset embedding

Vite's production build (`web/dist/`) has content-hashed filenames that aren't known ahead of time, so they can't be hand-written as static `import` statements. A codegen step solves this:

- **`scripts/generate-assets-manifest.js`**: run after `vite build` produces `web/dist/`. Walks the directory recursively and writes `server/generatedAssets.js`, containing one `import x from "<relative-path-into-web/dist>" with { type: "file" }` statement per discovered file (Bun's mechanism for embedding arbitrary files into a compiled binary), plus an exported map from URL path (e.g. `/assets/index-a1b2c3.js`) to the imported file reference.
- `server/generatedAssets.js` is generated, not hand-maintained, and is gitignored (same treatment as `web/dist/` itself — regenerated by the build step, never committed).
- `server/cli.js`'s static-serving logic reads from this map: on a GET request not matching `/api/*`, look up the request path in the manifest; if found, serve it with the correct content-type; if not found (client-side route), fall back to `/index.html`.

## Hook logic reuse

`hooks/gsd-web-hook.js` is refactored minimally:
- `handle(input)` is unchanged — no behavior change to the existing, already-tested hook logic.
- The `require.main === module` block's stdin-reading + `JSON.parse` + `handle()` + `process.exit(0)` sequence is extracted into an exported `runHookFromStdin()`. The script's own CLI block now just calls `runHookFromStdin()`. `server/cli.js`'s `hook` subcommand calls the same function (imported from `hooks/gsd-web-hook.js`).
- This guarantees the compiled binary's `hook` subcommand and the classic `node hooks/gsd-web-hook.js` invocation behave identically, since they share the exact same code path.

## Install-hook reuse

`scripts/install-hook.js` is refactored the same way:
- `mergeHookConfig(existing, hookCommand)` (already implemented and tested) changes its second parameter's meaning slightly: from "a script path to prefix with `node `" to "the full command string to register" — callers now pass the complete command (`"node /abs/path/hooks/gsd-web-hook.js"` or `"/abs/path/to/binary hook"`), not just a script path. This is a small, mechanical signature change; existing tests are updated to pass a full command string instead of a bare path.
- The backup-then-read-then-merge-then-write sequence (currently inline in the `require.main === module` block) is extracted into an exported `installHooks(hookCommand, settingsPath)`, where `settingsPath` defaults to `path.join(os.homedir(), '.claude', 'settings.json')` but can be overridden — making it unit-testable against a temp file without touching the real settings file, unlike before.
- The classic npm CLI block calls `installHooks(`node ${absoluteHookScriptPath}`)`.
- `server/cli.js`'s `install-hook` subcommand calls `installHooks(`${process.execPath} hook`)` — `process.execPath` correctly resolves to the compiled binary's own path when running as a compiled Bun executable.

## Multi-platform build

`npm run build:binary`:
1. Runs `npm run build:web` (existing script, unchanged) to produce `web/dist/`.
2. Runs `node scripts/generate-assets-manifest.js` to produce `server/generatedAssets.js`.
3. Runs `bun build --compile --target=<platform> server/cli.js --outfile dist-bin/gsd-web-<platform>` once per target: `darwin-arm64`, `darwin-x64`, `linux-x64`, `linux-arm64`, `windows-x64` (Bun's supported `--target` values for cross-compilation).
4. All outputs land in `dist-bin/`, which is gitignored.

Building requires the `bun` CLI to be installed on the build machine (via `brew install bun` or Bun's install script) — this is a build-time tool, not an npm dependency, and is not required for `npm run dev`/`npm start`/`npm test`.

## Error handling

- If `server/generatedAssets.js` doesn't exist when `server/cli.js`'s `serve` subcommand runs (e.g., someone runs the binary-only entrypoint without having run the build step — shouldn't happen via the documented `build:binary` flow, but worth a clear failure), fail with an explicit error message rather than a confusing runtime crash on a missing import.
- `install-hook` subcommand reuses the exact same backup-before-write safety behavior as the existing script (Task 14): back up the real `~/.claude/settings.json` before merging, never overwrite without a backup.
- The `hook` subcommand inherits the existing hook's "never throw, always exit 0" guarantee unchanged, since it calls the identical `handle()`/`runHookFromStdin()` code.

## Testing

- Unit tests for `scripts/generate-assets-manifest.js`'s file-discovery/import-statement-generation logic, against a small fixture directory (not a real Vite build) — verifying the generated file's structure (correct relative import paths, correct URL-path keys) without needing Bun installed to run this test.
- Unit tests for the refactored `installHooks(hookCommand, settingsPath)`, using a temp `settingsPath` — extending the existing idempotency/preserves-unrelated-hooks tests from Task 14 to the new signature.
- Unit test for `runHookFromStdin()` extraction, confirming it's callable and behaves identically to the existing `handle()`-based tests (no new behavior, just confirming the refactor didn't change anything observable).
- Manual smoke test (this machine, `darwin-arm64` target only — the only one that can actually execute here): run `npm run build:binary`, execute the resulting binary directly, confirm `/api/health` and `/` (embedded index.html) respond correctly, pipe a sample hook JSON payload into `<binary> hook` and confirm it writes a status file, run `<binary> install-hook` against a scratch settings file path (not the real `~/.claude/settings.json`) and confirm it merges correctly.
- The other four platform targets can only be build-verified (the file exists, has a reasonable size, `file <path>` reports the expected format) on this machine — they cannot be executed here.
