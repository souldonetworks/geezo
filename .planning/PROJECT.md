# GSD Run Dashboard

## What This Is

A local, read-only web dashboard for GSD (Get Shit Done) projects. It shows roadmap/progress status, live subagent activity, and the last git milestone tag for every registered project, all served from a single Node.js/Express + React app running on localhost. This ingest retroactively documents a project that is already built, tested, and committed on `main` — it is not greenfield.

## Core Value

You can check any registered GSD project's phase progress, current status, and live subagent activity from the browser, instead of running GSD status commands in a terminal.

### Out of Scope

<!-- Explicit boundaries. Includes reasoning to prevent re-adding. -->

- Multi-tenant / hosted / authenticated deployment — single-user, localhost-only tool by design; no auth layer planned.
- Correlating a running subagent to a specific phase/plan number — hook only knows the subagent's own short task description, not GSD's phase state; showing more would require fragile cross-referencing.
- Git network operations (fetch/push) from the dashboard — local-refs-only constraint keeps the tool read-only and side-effect-free.
- Cross-platform (Linux/Windows) "Convert to GSD project" terminal launch — the feature depends on `osascript` GUI/window-server access; explicitly macOS-only in both the dashboard SPEC and the packaging SPEC.
- Docker packaging — considered and rejected because the convert-to-GSD feature needs `osascript` GUI access a container can't provide; superseded by single-binary (Bun) packaging.
- CI/release automation for multi-platform binary builds — `npm run build:binary` is manual/local-only per SPEC; no automated release pipeline planned.

## Context

- This is a **brownfield ingest**: the dashboard core (SPEC 1 + SPEC 2 — project registry, ROADMAP.md/STATE.md/gsd.db parsing, live agent activity via hook + SSE, git milestone detection, convert-to-GSD flow, scan-folder discovery) is already fully implemented, tested (37 passing tests under `tests/server`, `tests/hooks`, `tests/scripts`), and committed on `main`.
- The single-binary packaging feature (SPEC 3) is fully designed but **not yet implemented anywhere in the repo** — confirmed by inspection: no `server/cli.js`, no `scripts/generate-assets-manifest.js`, no `server/generatedAssets.mjs` exist yet.
- Target runtime: Node.js is the primary runtime for development (`npm run dev` / `npm start` / `npm test`). Bun is used **only** for the optional single-binary packaging build (`npm run build:binary`) — it is a build-time tool, not a dependency of normal development.
- Existing stack (already in place): Node.js (CommonJS) + Express backend, `gray-matter` for YAML frontmatter parsing, Node's built-in `node:test`/`node:assert/strict` for backend tests, React + Vite frontend, `concurrently` for local dev orchestration.
- All persistent tool state (project registry, settings, live-activity status files) lives under `~/.claude/gsd-web/` — never inside a tracked project repo. Tests override this location via `GSD_WEB_HOME_OVERRIDE` to avoid touching the real user home directory.

## Constraints

- **Scope**: Single-user, localhost-only, no auth, not multi-tenant/hosted — this is a personal dev tool, not a service.
- **Read-only**: The dashboard is a read-only viewer over GSD's own state files (`.planning/ROADMAP.md`, `.planning/STATE.md`, `.gsd/gsd.db`) — never a replacement for or writer of those files.
- **Git safety**: Git operations use `execFileSync('git', [...])` with array args, never a shell string, to avoid injection; local refs only, no `git fetch`/`push`.
- **Hook safety**: The Claude Code hook script must never throw uncaught — it must not block the user's Claude Code session. All hook logic is wrapped in try/catch and always exits 0.
- **State isolation**: `scripts/install-hook.js` modifies the global, shared `~/.claude/settings.json` — only ever run explicitly by the user (`npm run install-hook`), never invoked automatically by build/test.
- **Staleness guard**: Live-activity status files older than 2 hours are ignored/hidden by the backend.
- **Packaging is additive**: The single-binary packaging layer (SPEC 3) must not change existing `npm run dev`/`start`/`test` workflows, and must not make "Convert to GSD project" cross-platform — it stays macOS-only regardless of packaging format.
- **No ADRs govern this project yet.** All architectural constraints above come from SPEC-level documents (`docs/superpowers/specs/2026-07-24-gsd-run-dashboard-design.md`, `docs/superpowers/plans/2026-07-24-gsd-run-dashboard-plan.md`, `docs/superpowers/specs/2026-07-24-single-binary-packaging-design.md`), not from ADRs. They are the highest-precedence source currently available and are treated as authoritative design context here, but — unlike a locked ADR — they are not durably un-overridable; if these choices (e.g. Bun-compiled single-binary distribution, macOS-only terminal-launch scope) should become permanent, they should be captured in a future ADR.

## Key Decisions

<!-- Decisions that constrain future work. No ADRs exist for this project — these are SPEC-level design choices carried forward, not formally locked. -->

| Decision | Rationale | Outcome |
|----------|-----------|---------|
| Single-user, localhost-only, no-auth architecture | This is a personal dev tool for one user checking their own GSD projects, not a hosted service | ✓ Good |
| Read-only viewer over `.planning/` and `.gsd/gsd.db` files | Avoids risk of corrupting GSD project state; dashboard should never be a second source of truth | ✓ Good |
| One status file per active subagent invocation (no shared append-only log) | Avoids read-modify-write locking; PreToolUse writes, PostToolUse deletes | ✓ Good |
| 2-hour staleness guard on live-activity status files | Handles crashed/orphaned subagent invocations without a cleanup daemon | ✓ Good |
| macOS-only (`osascript`) scope for "Convert to GSD project" | Feature needs GUI/window-server terminal-launch access; no cross-platform equivalent implemented | ✓ Good (accepted limitation) |
| Docker packaging rejected; pivoted to Bun-compiled single-binary distribution | Docker containers can't provide the GUI/window-server access `osascript` needs for convert-to-GSD | ✓ Validated in Phase 7 |
| Bun used only for `build:binary`, never for dev/test | Keeps primary Node.js/npm developer workflow unaffected by the optional packaging feature | ✓ Validated in Phase 7 |
| Asset embedding via generated, gitignored `server/generatedAssets.mjs` | Bun's file-embedding mechanism requires static `import ... with { type: "file" }` statements; codegen keeps this in sync with `vite build` output | ✓ Validated in Phase 7 |
