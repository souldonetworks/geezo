# Geezer-style project assessment — v2

Apply the same disciplined method as the Existing Project Assessment used for the Puppet Governed Remediation Gateway, adapted to this project's actual purpose. Do not copy that project's claims, recommended components, estimates or customer assumptions into unrelated projects.

1. Inventory the supplied project name, path, revision and evidence boundary. Documentation is intent unless supplied implementation supports it. A portfolio name is a discovery lead, not inspected reuse evidence.
2. Identify at most eight meaningful capabilities. Separate status (implemented, partial, planned only, missing, unknown) from verification (inspected only, historical tests reported, not verified). No project commands or tests were executed by this assessment. Historical tests require a supplied source reporting them and their limits. Missing means absent from the examined path, never proof of workspace-wide absence.
3. Prefer reuse, extension, integration or upstream contribution where evidence supports it. Explain alternatives and the remaining gap. Name uninspected cross-project candidates only as proposed discovery leads. Do not conflate runtime upgrades, packaging, previews, released capability and customer outcomes.
4. Propose the smallest useful experiment, explicit scope/exclusions, observable positive and negative cases, and honest verification criteria. Scale to investment: personal work and informal demonstrations do not need invented enterprise buyers or revenue.
5. Describe up to four investment tiers (experiment/lab, pilot, production, optional integration). Effort and confidence are unknown unless estimates exist in the evidence; suggested scope and acceptance criteria are proposed, not commitments. Implementation, productization and ongoing support costs remain distinct. Do not sum overlapping estimates.
6. State customer evidence, ownership, commercial attribution, supportability, licensing uncertainties, off-ramp and decision gates. Do not assume lack of a license file is legal clearance. Leave dates, money and named commitments unknown unless supported.

In addition to the seven executive brief sections, return an assessment object:
{"summary":"Short reuse-first assessment with explicit verification boundary","capabilities":[{"capability":"name","component":"project/path or unknown","status":"implemented|partial|planned only|missing|unknown","verification":"inspected only|historical tests reported|not verified","verificationDetail":"Scope and limits of historical evidence or inspection","evidenceRefs":["relative/file:line"],"limitations":"remaining gap","reuseApproach":"proposed reuse/extend/integrate/defer and why"}],"investmentTiers":[{"tier":"experiment|pilot|production|optional","scope":"proposed bounded work","effort":"unknown unless source provides an estimate","confidence":"unknown unless sourced","acceptance":"proposed validation criteria","evidenceRefs":[]}],"limitations":["No project commands or tests executed; source inspection only."]}

Cite files and line numbers actually supplied. Claims about implementation require implementation evidence rather than a README alone; otherwise mark planned only, partial or unknown. A hypothetical or unknown capability can have no references if its limits say why. Keep the summary concise and the unknowns visible. Return JSON only.

Also return a top-level suggestedTags array of up to eight concise lowercase kebab-case topic tags (technologies, problem domains, workflows). Base tags on the project evidence, and avoid generic filler. Never assign personal/work classification; the user controls that field. Suggested tags are discovery leads rather than confirmed capabilities.
